# Juliya typography and adoption

The filename is retained for existing references. This guide covers only the four explicitly supported locales and only adapters supported by the verified release; other locales retain native wrapping.

Prefer the published `@oddmash/juliya` library for eligible editorial headings, hero copy, descriptions and other meaningful prose in Korean, English, Japanese and Simplified Chinese on Oddmash websites when the actual locale adapter and release support it. Juliya was formerly Kowrap; preserve existing `@oddmash/kowrap` deployments until an authorized, verified dependency migration. Do not blindly replace names in historical examples. Inspect the current package exports, documentation, framework, version and existing dependency policy before implementation. Use an existing compatible version or a pinned reviewed release; never guess an API. Start with native locale-appropriate CSS and readable measure as the fallback, then integrate the supported adapter (React, Vue, Svelte, DOM or core) that fits the actual runtime. Keep static/SSR content readable before hydration and without JavaScript.

Do not wrap code, URLs, identifiers, form inputs, screen-reader-only text, or unrelated locales indiscriminately. Preserve headings, links, emphasis, selectable text, copy, keyboard access and manual breaks. Avoid nested wrappers, forced fixed widths, layout shifts, redundant observers, unnecessary client bundles and changes to semantic markup. For mixed languages, narrow labels or unsupported contexts, use native CSS when Juliya would worsen behavior. Record justified exceptions.

Test real supported-language and mixed-script content at representative narrow and wide widths, with actual and fallback fonts, font loading, resize, dynamic content, inline markup, long words, whitespace, zoom, and SSR/hydration where applicable. Compare native CSS and Juliya at equal measured widths and typography. Check human readability, overflow, unexpected extra lines, fragmented words or semantic phrases, punctuation, text preservation and measurable layout/performance effects. Do not claim every line improves; preserve a working fallback.

## Consumer-to-library improvement loop

1. Isolate the problem in the consumer using the actual copy, width, font, browser, package version, adapter and minimal reproducible input. Save expected and actual behavior without sensitive data.
2. Determine whether the cause is consumer CSS/layout, unsupported usage, integration, or Juliya itself. Fix consumer misuse locally; do not hide an engine defect with repeated handcrafted line breaks or global hacks.
3. When the evidence identifies a Juliya defect and cross-repository fixes are authorized, search or open a linked issue in Oddmash/juliya, add a regression test that fails on the old behavior, implement the smallest compatible engine/adapter fix, run unit, package, relevant browser, framework and hydration tests, then open a separate reviewable PR. If not authorized, report the issue and evidence rather than editing another repository.
4. Follow the library's release and review policy. Do not silently publish or consume an unreleased commit. Verify the approved release/artifact in the actual consumer, rerun rendering checks, and record the resolved version and remaining limitations. Keep the consumer functional while an upstream fix is pending.

Do not introduce a Juliya dependency cycle; the Juliya site may use its own supported local build per its product instructions. Treat this loop as continuous product feedback, not a requirement to manufacture issues.
