# Oddmash UX design

Read the product brief and inspect the actual current workflow. Identify the user, their goal, entry point, first useful action, and what success looks like.

- Map the shortest coherent task path and the decisions the user must make. Keep frequent actions discoverable and place contextual controls near their consequences. Preserve supported contracts, not incidental layout. For every visible control, name the distinct user decision or accessibility need it serves. If another control or native behavior already serves that need, combine or remove it.
- Specify empty, loading, error, success, disabled, and recovery states where they affect the task. For consequential actions, communicate what will change, preserve drafts when possible, and provide recovery or explicit confirmation.
- Prefer familiar controls and clear labels; use icons as supporting signals where meaning is not obvious. Design keyboard access, focus order, responsive layouts, touch targets, and localized label lengths from the beginning.
- For a project or resource card with one clear primary destination, make its title, preview and otherwise unused card area a generous native-link target where appropriate. Keep a single primary focusable anchor with a meaningful accessible name and separate sibling links for distinct actions; never nest anchors, replace native links with container click handlers, or let the expanded hit area intercept secondary links, selectable text or controls. Preserve modifier-click, open-in-new-tab, keyboard focus and touch behavior. For familiar destinations such as GitHub and npm, prefer concise recognizable icon links with localized accessible names and adequate hit areas over repetitive text CTAs. Verify the exact public target and localized document path; show a registry icon only for a package actually published there. Use text for destinations whose icon alone is ambiguous, and retain distinct documentation, live-product or setup actions when they serve a different user decision. Route the visual response to [control microinteractions](../oddmash-motion-microinteraction/SKILL.md).
- When comparable cards expose the same kinds of actions, default their action group to the lower logical end of each card (bottom right in left-to-right layouts), with consistent spacing and alignment despite different copy lengths. Allow content to grow and groups to wrap at narrow widths; do not impose identical card heights or footer actions on unrelated card types. Use actual local documentation for the documentation destination where available, keep public source links independent, and omit unavailable destinations rather than displaying inactive or guessed links. Aim for at least 44 by 44 CSS px of usable target area for standalone icon actions without enlarging the glyph or overlapping nearby controls; this is a comfortable touch goal, not the WCAG AA minimum. Verify actual click routing from the expanded primary area and each secondary target, logical keyboard focus, and alignment with unequal descriptions and localized labels at narrow and wide widths.
- Compare alternatives using real tasks, not visual preference alone. For a material redesign or repeated feedback, compare the current flow with a simpler flow, including removal or consolidation. Choose the one that communicates the outcome with the fewest necessary decisions. Separate observed usability evidence from assumptions. Define acceptance for task completion, errors, clarity, and accessibility; do not claim user research that was not conducted.
- Deliver a reviewable flow, key states, open decisions, and verification plan. Use [brand design](../oddmash-brand-design/SKILL.md) for visual identity, [motion design](../oddmash-motion-design/SKILL.md) when movement has a functional role, and [developer documentation](../oddmash-developer-documentation/SKILL.md) for library learning and reference journeys.

- For applicable asynchronous surfaces, select relevant states rather than adding controls for every possible state: initial loading, refreshing with existing data, partial success, empty/no-match, offline, timeout, retry, permission denied, expired session, stale data, and fatal error. Explicitly mark inapplicable states.
- Specify the loading and recovery behavior that the task actually requires. Use [feedback motion](../oddmash-motion-feedback/SKILL.md) for skeletons, progress and timing only when applicable. Keep existing data visible during refresh when safe; use determinate progress when real progress is known.
- Define hover, focus-visible, pressed, selected, disabled, pending, invalid and read-only states; explain disabled actions where useful. Include keyboard, touch, drag alternatives, copy/paste, long content, overflow, safe areas, and zoom. Prevent duplicate submissions and preserve form input after recoverable errors.
- Design confirmations proportional to consequences, undo where feasible, clear field errors, accessible announcements and predictable focus after navigation, dialog closure or deletion. Avoid destructive defaults, deceptive consent, forced sign-up and misleading urgency.
- Check onboarding, first run, account settings, cancellation, sign-out and account deletion when applicable; ensure every user journey has an exit and recovery path.
- Read [accessibility](../oddmash-accessibility/SKILL.md) and [security and privacy](../oddmash-security-privacy/SKILL.md) for acceptance criteria before handoff.

- Where relevant, design authentication and recovery screens, email verification, session expiry, saved/draft/conflict indicators, unsaved-change confirmation, import/export, undo, upload progress and optimistic rollback; preserve the user's task across recoverable interruptions. Use [sharing](../oddmash-sharing-distribution/SKILL.md) and [internationalization](../oddmash-internationalization/SKILL.md) for affected surfaces.

For operational dashboards, workflow histories and monitoring consoles, route the task hierarchy and responsive data presentation to [dashboard design](../oddmash-dashboard-design/SKILL.md). Preserve the existing UX and accessibility requirements.

- Organize long settings by the user's task, surface high-frequency actions and current effective state before scrolling, and keep save/cancel actions readily reachable. Preserve drafts across internal sections; confirm before discarding on navigation, sign-out or reload, using an accessible dialog and native browser fallback where needed. Verify cancellation retains the draft, confirmation discards only unsaved edits, and successful saves clear the guard. Distinguish read-only policy from editable controls; never imply unavailable permissions.
