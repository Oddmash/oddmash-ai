# Oddmash git workflow

Read the [organization agreements](https://github.com/Oddmash/.github/blob/main/AGENTS.md), target AGENTS.md, CONTRIBUTING.md, templates and branch/release rules first. Those documents and enforced protections govern authority; this skill is a reusable workflow, not a waiver.

- Verify checkout path, remote owner/name, current branch, base revision and status before edits. Preserve existing user work, unrelated changes and authorship. Fetch using normal authorized access when available; do not assume stale local state is current.
- For JavaScript and TypeScript dependency, workspace, CI or package-manager changes, use the organization package-manager pin and follow [package management](references/package-management.md). Preserve existing dependency versions and consumer contracts.
- Before an authorized implementation, search the target repository for an existing issue covering the same scope. Reuse it instead of creating a duplicate. If none exists, register a scoped issue using the repository template before editing, with the problem, intended change, observable acceptance criteria as Markdown bullets or checkboxes, and exclusions. Do not create issues for read-only consultation or when issue creation is not authorized; record the missing tracking link when blocked.
- For product repositories, branch focused implementation work from current `develop`, target `develop`, and open a verified consolidated release PR from `develop` to `main`. Synchronize main changes back into develop through a reviewed PR without rewriting historical commits. Verify both product branches require the trusted aggregate verify check. If protection is missing, report the administrator action required before relying on automatic merge. For infrastructure or reusable tooling repositories declaring the main-only exception, branch from current `main` and target `main` directly; do not introduce an integration branch. Preserve existing in-flight work and inspect the prospective diff before an authorized PR retarget. Never delete branches or weaken protections as incidental work.
- Follow local branch naming rules; absent a convention, prefer feat/, fix/, docs/, refactor/, test/ or chore/ with a concise lowercase slug. Keep required CI on both implementation and release PRs, cancel superseded PR runs, use existing change-scope detection and dependency caches, and preserve stable aggregate checks. Avoid redundant integration-push checks and unsolicited preview deployments; publish only an explicitly authorized release from the approved main revision or repository release event.
- **Issue linkage gate:** Before opening any implementation PR, verify a real issue number and repository and ensure the PR body contains an explicit reference. If no issue exists, create one first; if blocked, stop before opening the PR and report the missing tracker. Put an explicit issue reference in every implementation PR body: `Refs #123` for partial, stacked or integration-branch work, or `Closes #123` only when merging into the default branch will satisfy the entire issue. Use one scoped reference on its own line in Related issue for topic and branch synchronization PRs. For a develop-to-default release PR, list each distinct included issue on its own line and close only completed issues. Use `Refs Owner/repository#123` or `Closes Owner/repository#123` for cross-repository tracking and keep umbrella issues open until every dependent change is verified. Multi-issue release PRs and cross-repository references require manual merge after CI and review. Do not use closing keywords as a substitute for acceptance evidence.
- Keep commits atomic and meaningful; follow repository convention, default to concise English imperative subjects. Stage intended paths only, inspect diff and status, exclude secrets, generated output unless required, and unrelated changes. Never rewrite shared history or discard user changes without explicit approval.
- When a commit materially implements a verified finding or advisory from any Oddmash agent, append the canonical `Co-authored-by` trailer for its actual authenticated GitHub account using the [organization agent attribution convention](https://github.com/Oddmash/.github/blob/main/AGENTS.md#agent-contribution-attribution). Credit only genuine contributions, not coordination or approval alone, deduplicate by account, preserve existing authorship, and never rewrite published history. Record the source thread or role when the same Lead identity posted coordinated advice. While composing the fix commit, compare the trailer with the authenticated author and canonical no-reply entry. After pushing, check the resulting commits with `git log --format='%h%n%(trailers:key=Co-authored-by)'` or the GitHub PR commits endpoint. If a published commit is missing credit, record the contribution in the PR evidence and retain the published history.
- Use English public issue/PR titles, bodies, review replies, commits and changelogs. Describe scope, rationale, linked issue, verification evidence, screenshots when applicable, compatibility/privacy/permissions and release implications. Open PRs ready for review by default, including while remote CI or review is pending. Only use a draft for an explicit request, materially incomplete implementation or missing essential evidence that would mislead review; record the reason and mark ready when resolved. Never treat ready status as approval or permission to merge.
- Run the target repository checks and inspect exact-head CI and review evidence. Address genuine findings with regression tests and mention the source reviewer in the original discussion with the fix and evidence, per [review collaboration](../oddmash-code-review-collaboration/SKILL.md). A resolved thread is not approval. Never fabricate checks, bypass branch protection or approve on behalf of a reviewer.
- Before handoff, retrieve the created or updated PR and verify its actual base branch and issue reference. Fix missing links before reporting completion. Before handoff, reconcile all outstanding inline and Conversation findings: fixed with evidence, unsupported with rationale, or unresolved with blocker. Never report reviews as handled solely because CI passed or a commit was pushed.
- Use normal merge commits for PR merges unless the maintainer explicitly requests another method. Do not auto-merge external contributions. Private PRs are eligible only if the current organization policy explicitly permits their repository identity and low-risk paths; any maintainer-authorized automated merging must satisfy the separate gated policy and exact-head checks. Do not merge or publish merely because a skill was invoked.
- After an authorized merge, verify the actual merge commit, linked issue state and acceptance criteria against the merged revision. Record relevant CI and test evidence in the issue or PR without exposing private data. Keep incomplete issues open with the remaining criteria and blockers, and close only completed issues when authorized. Do not treat a linked or merged PR as proof of full issue completion.
- Derive tags/releases from the repository version policy and exact merged revision. Verify release artifacts using [release management](../oddmash-release-management/SKILL.md). Prefer a new revert or corrective PR for shared history; stop on conflicts or ambiguous destructive operations rather than force-pushing.
- Report branch, commit/PR links, exact head, checks, review state and remaining blockers. Distinguish local, remote, merged and released status.
