# Oddmash git workflow

Read the [organization agreements](https://github.com/Oddmash/.github/blob/main/AGENTS.md), target AGENTS.md, CONTRIBUTING.md, templates and branch/release rules first. Those documents and enforced protections govern authority; this skill is a reusable workflow, not a waiver.

- Verify checkout path, remote owner/name, current branch, base revision and status before edits. Preserve existing user work, unrelated changes and authorship. Fetch using normal authorized access when available; do not assume stale local state is current.
- Before an authorized implementation, search the target repository for an existing issue covering the same scope. Reuse it instead of creating a duplicate. If none exists, register a scoped issue using the repository template before editing, with the problem, intended change, observable acceptance criteria and exclusions. Do not create issues for read-only consultation or when issue creation is not authorized; record the missing tracking link when blocked.
- Use a focused branch from the verified base. Follow local naming rules; absent a convention, prefer feat/, fix/, docs/, refactor/, test/ or chore/ with a concise lowercase slug.
- Put an explicit issue reference in every implementation PR body: `Refs #123` for partial, stacked or integration-branch work, or `Closes #123` only when merging into the default branch will satisfy the entire issue. Use `Owner/repository#123` for cross-repository tracking and keep umbrella issues open until every dependent change is verified. Do not use closing keywords as a substitute for acceptance evidence.
- Keep commits atomic and meaningful; follow repository convention, default to concise English imperative subjects. Stage intended paths only, inspect diff and status, exclude secrets, generated output unless required, and unrelated changes. Never rewrite shared history or discard user changes without explicit approval.
- When committing a substantive fix derived from Oddmash Reviewer feedback, add the `Co-authored-by: oddmash-reviewer[bot] <360059368+oddmash-reviewer[bot]@users.noreply.github.com>` trailer after a blank line. Credit only genuine contributions and preserve existing authorship; never rewrite already-pushed commits solely to add this trailer.
- Use English public issue/PR titles, bodies, review replies, commits and changelogs. Describe scope, rationale, linked issue, verification evidence, screenshots when applicable, compatibility/privacy/permissions and release implications. Open PRs ready for review by default, including while remote CI or review is pending. Only use a draft for an explicit request, materially incomplete implementation or missing essential evidence that would mislead review; record the reason and mark ready when resolved. Never treat ready status as approval or permission to merge.
- Run the target repository checks and inspect exact-head CI and review evidence. Address genuine findings with regression tests and reply in their original discussion with the fix and evidence; request scoped verification, not repeated whole-PR reviews, per [review collaboration](../oddmash-code-review-collaboration/SKILL.md). A resolved thread is not approval. Never fabricate checks, bypass branch protection or approve on behalf of a reviewer.
- Before handoff, reconcile all outstanding inline and Conversation findings: fixed with evidence, unsupported with rationale, or unresolved with blocker. Never report reviews as handled solely because CI passed or a commit was pushed.
- Use normal merge commits for PR merges unless the maintainer explicitly requests another method. Do not auto-merge external contributions. Private PRs are eligible only if the current organization policy explicitly permits their repository identity and low-risk paths; any maintainer-authorized automated merging must satisfy the separate gated policy and exact-head checks. Do not merge or publish merely because a skill was invoked.
- After an authorized merge, verify the actual merge commit, linked issue state and acceptance criteria against the merged revision. Record relevant CI and test evidence in the issue or PR without exposing private data. Keep incomplete issues open with the remaining criteria and blockers, and close only completed issues when authorized. Do not treat a linked or merged PR as proof of full issue completion.
- Derive tags/releases from the repository version policy and exact merged revision. Verify release artifacts using [release management](../oddmash-release-management/SKILL.md). Prefer a new revert or corrective PR for shared history; stop on conflicts or ambiguous destructive operations rather than force-pushing.
- Report branch, commit/PR links, exact head, checks, review state and remaining blockers. Distinguish local, remote, merged and released status.
